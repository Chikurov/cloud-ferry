# Cloud Ferry — ТЗ на реализацию редизайна «Спокойный мастер» V2

Дата: 15 ноября 2026. Адресат: coding-агент, работающий с исходным проектом.

## 1. Задача и приоритет решений

Переработать интерфейс существующего Cloud Ferry по выбранному концепту «Спокойный мастер» V2. Сохранить рабочую логику скачивания из облака на сервер Umbrel. Это обновление пользовательского интерфейса и сценариев, а не переписывание backend или переход на новый стек.

Пользователь остановился на текущей композиции V2. Новые концепции не разрабатывать. Две обязательные доработки относительно показанного макета:

1. Исправить светлую тему: текст сливается с фоном и местами не читается. Это блокирующий дефект, а не косметическое пожелание.
2. Сделать оформление чище и выразительнее. Сейчас поверхность слишком напоминает стандартные панели Chrome и табличные интерфейсы. Добиться качества точной типографикой, выравниванием, аккуратными поверхностями и акцентами, сохранив компактность.

Приоритет: последние пожелания пользователя → это ТЗ → реальные контракты приложения → предыдущие аудиты → демонстрационный макет. При конфликте дизайна с контрактом сначала найти минимальную совместимую реализацию, затем явно описать оставшееся расхождение. Макет не подтверждает серверные возможности.

Не переносить в production демонстрационные логины, размеры, прогресс 42 %, фиктивные файлы, успешный вход без проверки и переключатель «Экран». Прототип проверялся на переходы и вычисления; полноценная браузерная проверка визуала не была выполнена. Последний отзыв пользователя подтверждает проблему светлой темы.

## 2. Что проверить в проекте до правок

- Прочитать локальные инструкции, команды сборки и проверок. Определить актуальную ветку и не затереть существующие изменения.
- Найти текущие компоненты/шаблоны, CSS темы, маршрутизацию диалогов и хранилище состояния. В ранее изученном архиве интерфейс находился в `internal/httpapi/web`; подтвердить путь в текущем checkout.
- Найти аналоги `homeMarkup()`, `methodSwitch()`, `openFlowStart()`, `preferredDest`, `createJob()`, `clientToken`, `StartIdempotent()`. Имена — ориентиры из архива, не основание создавать дублирующие реализации.
- Зафиксировать реальные методы входа, способы отмены/паузы, API списков, ограничения выбора, оценку объёма и состояния задач.
- Проверить, зависит ли сохранение аккаунта от назначения папки. Если зависит, разделить эти операции минимально; убрать шаг визуально недостаточно.
- Снять исходные состояния на тестовых данных. Не входить в реальные аккаунты и не запускать скачивание пользовательских файлов без соответствующей авторизации.

Результат этого этапа — короткая карта изменяемых модулей и обнаруженных ограничений. Далее переходить к реализации без нового согласования каждого отступа.

## 3. Границы изменений

Входит: обе темы, визуальная система, стартовый экран, подключение, главный экран, детали аккаунта, выбор файлов, выбор назначения, проверка перед запуском, состояния скачивания, ошибки и уведомления, адаптивность, доступность и необходимые регрессионные проверки.

Не добавлять новые облачные провайдеры, планировщик, синхронизацию в обе стороны, удаление облачных файлов, аналитику, новые разделы навигации, декоративную карусель с единственным диском. Невозможность удалить созданную папку зафиксирована, но отдельный файловый менеджер и удаление папок не входят в этот редизайн.

Сохранить существующие ограничения безопасности, валидацию назначения, защиту от повторного запуска и обработку ошибок. Удаление текста предупреждения не означает удаление соответствующей проверки.

## 4. Визуальная система

### 4.1. Характер интерфейса

Спокойный минималистичный инструмент с узнаваемым синим акцентом. Основные действия заметны; вторичные не спорят с ними. Один уровень основных поверхностей, минимум вложенных рамок. Не обводить каждую подпись, строку метаданных и группу кнопок отдельной серой коробкой.

«Богаче» в рамках этой задачи означает:

- выраженная, но сдержанная иерархия заголовка, содержимого и вспомогательного текста;
- согласованные пропорции кнопок и карточек;
- чистые нейтральные фоны с небольшим различием уровней;
- лёгкая глубина крупных поверхностей там, где она помогает их отделить;
- одинаковый набор иконок и согласованная толщина линий;
- качественные hover, focus, pressed, selected, disabled и loading состояния.

Не добавлять стеклянные панели, крупные градиенты, тяжёлые тени, декоративные показатели, огромные иконки и анимацию ради украшения. Не компенсировать скучный вид увеличением пустых зон.

### 4.2. Типографика и геометрия

Стартовые значения для реализации; уточнять по реальному рендеру, сохраняя систему.

| Элемент | Требование |
|---|---|
| Семья | Один system sans stack на всём интерфейсе; Inter только если уже поставляется проектом |
| Основной текст | 14 px, line-height около 1.45–1.5, weight 400 |
| Кнопки и названия файлов | 14 px, weight 500 |
| Заголовки | 18–20 px, weight 600; без случайных размеров между экранами |
| Вторичные сведения | 12–13 px; не использовать слабый контраст как замену иерархии |
| Поля на телефоне | Не меньше 16 px для ввода |
| Числа прогресса | Tabular numerals; процент 20–22 px, без огромного дисплейного размера |
| Шкала отступов | 4, 8, 12, 16, 20, 24, 32 px |
| Внешние поля | Примерно 24 px desktop, 12–16 px mobile |
| Основная поверхность | Радиус 14–16 px |
| Кнопки и поля | Радиус 9–10 px, общая высота около 40 px desktop |
| Выделенная строка | Радиус 10 px; зазор до соседней строки 6–8 px |
| Диалог выбора | Ширина примерно 680–760 px; высота по содержимому с ограничением окном |
| Авторизация и аккаунт | Более узкие поверхности около 400–440 px |
| Touch | Эффективные области нажатия около 44 × 44 px без пересечения |

У каждой группы текстов общая левая линия. Иконки центрировать относительно строки, а не случайной высоты контейнера. Одинаковые отступы в шапке, содержимом и футере одной поверхности. Длинные пути переносятся; важные части имени и действия остаются доступны. Не обрезать проблему через `overflow:hidden` на всём приложении.

### 4.3. Светлая и тёмная темы — обязательное исправление

Создать семантические CSS-переменные для фона приложения, поверхности, приподнятой поверхности, основного и вторичного текста, границ, акцента, текста на акценте, выделения, фокуса, успеха, предупреждения и ошибки. Определить полный набор для каждой темы. Не смешивать независимые переключатели темы разных компонентов.

Следующие цвета — отправная палитра для проверки, а не доказательство достаточного контраста каждой комбинации:

| Токен | Светлая | Тёмная |
|---|---|---|
| Фон приложения | `#F4F6F9` | `#151920` |
| Поверхность | `#FFFFFF` | `#20262F` |
| Вторичная поверхность | `#EDF1F6` | `#2A323E` |
| Основной текст | `#182333` | `#EFF3FA` |
| Вторичный текст | `#526174` | `#B1BDCE` |
| Акцент | `#185CCD` | `#A9C8FF` |
| Текст на акценте | `#FFFFFF` | `#102A50` |
| Выделенная строка | `#E8F0FF` | `#293C57` |
| Обычная граница | `#DCE2EB` | `#3A4554` |

Порядок исправления:

1. Воспроизвести дефект в реальном браузере и посмотреть computed styles текста и фактического фона. Причина пока не установлена: проверить наследование, специфичность, opacity родителя, браузерные стили форм и область действия темы.
2. Явно задать цвет и фон для input, textarea, select, menu, dialog и toast. Проверить placeholder, выделение текста и browser autofill.
3. Если используется `light-dark()`, гарантировать согласованный `color-scheme` на корне приложения и порталах. Иначе использовать явные `[data-theme]` наборы переменных. Не менять только фон, оставляя цвета дочерних компонентов от другой темы.
4. Проверить основной/вторичный текст на обычной и выделенной поверхности, текст кнопок, ошибки, подписи прогресса, раскрытые меню и подсказки в обеих темах.
5. Проектный порог приёмки: минимум 4.5:1 для обычного и вторичного текста; минимум 3:1 для крупных надписей и значимых границ/индикаторов состояния. Декоративные разделители не обязаны выглядеть столь контрастно. Проверить программно реальные пары после вычисления прозрачности.
6. Выбранное состояние обозначать галочкой и фоном; ошибку — текстом и подходящим индикатором. Одного цвета недостаточно.

Переключатель темы — в шапке. Первый визит может следовать системной теме, явный выбор сохраняется локально. Переключение не сбрасывает форму, выбранные файлы, папку и прогресс. Задать тему до первого видимого кадра, чтобы не было вспышки противоположного оформления. Проверить меню и диалоги, которые рендерятся вне основного контейнера.

### 4.4. Выделение файлов

Каждая строка имеет собственный фон, border-radius и постоянную толщину границы. Между строками есть зазор. Выделение не увеличивает высоту и ширину строки. Не использовать отрицательные отступы и наложенные контуры соседних строк.

При выборе нескольких соседних строк скругления независимы и не пересекаются. Focus ring не обрезается. Checkbox, навигация внутрь папки и выбор строки должны иметь однозначные зоны: нажатие на раскрытие не должно одновременно переключать выбор.

## 5. Сценарии и состояния

### 5.1. Первый запуск

Шапка Cloud Ferry, ниже компактная строка «Подключить диск» с плюсом и понятной областью нажатия. Общая левая линия с основным содержимым. Не центрировать строку по высоте окна. Увеличение высоты браузера не должно удалять кнопку от заголовка.

Название действия универсальное. Конкретный сервис указывать внутри подключения. Не показывать будущие недоступные провайдеры.

### 5.2. Подключение

Заголовок «Подключить диск». Доступные способы видны до ввода данных. Сохранить «Пароль приложения» и «Токен». Если в актуальной установке настроен и работает существующий вход через Яндекс, сохранить его; не скрывать рабочую возможность только потому, что в демо было две вкладки. Не показывать неработающий OAuth как готовое действие.

Поля пароля: «Логин Яндекса», «Пароль приложения». Указать именно пароль приложения, дать существующую проверенную ссылку для создания. Сохранить autofill. Ссылки открывать с сохранением введённого логина и состояния формы.

Поля токена: «Токен доступа», placeholder «Вставьте токен или полный JSON ответа». Принимать только форматы, поддержанные сервером. Помощь «Где получить токен?» раскрывает короткую последовательность действий и проверенную ссылку. Не переносить из макета текст про демонстрационный токен. Не обещать автоматическую вставку без реализованного OAuth.

Условия тарифа, доступности WebDAV, время жизни токена и инструкции проверить по текущей интеграции и официальным источникам перед фиксацией текстов. Не диагностировать задержку активации пароля только по общему 401.

На отправке: «Подключаем…», защита от повторной отправки. На ошибке: точное сообщение рядом с формой, восстановить возможность исправить и повторить. Не очищать несекретные поля без причины; секреты не сохранять в URL, логи или localStorage.

Успех: после реального подтверждения подключения открыть главный экран и кратко показать «Диск подключён». Убрать выбор серверной папки и отдельный экран успеха из авторизации.

### 5.3. Главный экран

Desktop: основной блок скачиваний и компактная карточка аккаунта. Mobile: вертикальная композиция. Сохранить визуальный баланс; не растягивать пустой блок до высоты окна.

До первого скачивания: заголовок «Скачивания» и кнопка «Скачать». Никакой пустой карточки задачи и набора пояснений «Скачиваний пока нет», «Нажмите кнопку», «Три шага».

Аккаунт: сервис, логин, статус и облачная ёмкость. Формат «Занято 138 ГБ из 2 048 ГБ» с реальными данными. Даже большие ёмкости здесь показывать в ГБ по пожеланию пользователя. Согласовать перевод байт и округление; неизвестная ёмкость не равна нулю. Не путать эту метрику со свободным местом сервера.

Статус доступности отражает реальный ответ. Во время проверки не показывать ложное «Доступен». Потеря связи с приложением и истечение авторизации — разные состояния.

### 5.4. Детали аккаунта и выход

Компактный диалог с крестиком. Логин и занятая облачная ёмкость. Убрать способ входа, повторный статус доступа, папку назначения и свободное место сервера. Сохранить одну семью шрифтов и согласованные строки.

Блок выхода с внутренними боковыми отступами: заголовок «Выйти из аккаунта», кнопка «Выйти». При активном скачивании текст «Активное скачивание остановится». Не добавлять фразу о сохранённых файлах. Не показывать предупреждение об активном скачивании, когда его нет.

Убрать «Войти заново» и дублирующую кнопку «Закрыть». Повторный вход доступен после выхода. Проверку соединения выполнять через существующую логику; отдельную постоянно видимую сервисную кнопку без понятного сценария убрать.

Если выход требует подтверждения, подтвердить конкретное действие один раз. После успешного ответа очистить связанное с аккаунтом состояние. При ошибке выхода не изображать успех. Не обещать удаление истории заданий, если backend её сохраняет.

### 5.5. Что скачать

Открывать выбор файлов с заголовком «Что скачать». Сверху компактная строка «Сохранить в», текущий путь и «Изменить».

Для первого скачивания использовать только доступную папку по умолчанию, подтверждённую backend. Если такой папки нет, показать «Выберите папку» и дать открыть выбор. Для повторного использовать последнюю выбранную папку после проверки доступности. Не подставлять `/downloads/yandex` из демо как универсальную константу.

Список: галочка, иконка, название, доступные метаданные. Количество файлов и размер показывать только при наличии корректных данных; не запускать дорогой рекурсивный обход каждого элемента только ради строки. Для отсутствующих данных использовать нейтральное состояние, не фиктивный ноль.

Нет горизонтальной ленты выбранного и постоянного «0 из 20». Лимиты брать из действующего контракта. В ранее проверенном сценарии — 20 папок и 100 файлов; подтвердить актуальность. При превышении отказать только в новом выборе, показать причину, сохранить возможность снять галочку и вернуться.

Режим «Весь диск» по умолчанию выключен. Если он поддерживается, находится в «Ещё». Включение явно меняет заголовок на «Выбран весь диск», рядом доступно «Выбрать отдельно». Возврат восстанавливает предыдущий ручной выбор. Если восстановлен черновик с целым диском, состояние явно видно.

Выбранная папка и дочерние файлы не должны давать двойной подсчёт. Частичный выбор родителя — indeterminate. Поведение вложенности согласовать с серверной семантикой; не потерять поддерживаемую глубину дерева из-за упрощённого демо.

Наличие папки на сервере обозначать «Папка есть на сервере». Это не подтверждение полноты и целостности всех файлов. Обновлять сведения после смены назначения. Не превращать наличие папки в безусловный запрет скачать её содержимое.

Редкие настройки убрать из основной области выбора в компактное раскрытие «Параметры», если они нужны текущему продукту. Сохранить существующие безопасные значения и реальные эффекты. Не добавлять противоречивые переключатели только потому, что они упоминались в ранних набросках.

### 5.6. Папка на сервере

Отдельный вложенный выбор из строки назначения. Текущий путь, «На уровень выше», список подпапок, вторичная «Создать папку», основная «Выбрать эту папку».

Переход внутрь папки меняет просмотр. Только «Выбрать эту папку» сохраняет назначение. «Назад» и крестик отменяют промежуточный просмотр и возвращают к предыдущему экрану со старым назначением. Облачный выбор сохраняется.

Создание: поле «Название папки», «Создать», отмена локальной формы. Проверять имя и на клиенте, и на сервере; не ослаблять ограничение разрешённого корня. После успеха обновить список и показать уведомление. Не выбирать созданную папку автоматически без явного понятного действия.

Ошибка доступа, отсутствие папки и загрузка списка — отдельные состояния. Не показывать «В этой папке нет подпапок», пока запрос не завершён. Не показывать свободное место в каждом просмотренном каталоге.

### 5.7. Проверка и запуск

Заголовок «Проверьте выбор». Строки «Что скачать», «Сохранить в», объём, если известен. У первых двух строк — «Изменить». Для большого выбора использовать компактную сводку с раскрытием, без десятков тегов и горизонтального скролла.

Кнопки «Назад» и «Скачать». Убрать повторяющиеся описания Яндекс Диска и Umbrel, сообщение «Файлы в облаке не удаляются», общий алёрт объёма и постоянную кнопку «Узнать объём».

Оценка объёма не должна удерживать пользователя без причины. При её ошибке явно показать «Объём не удалось определить»; позволить запуск только если серверный контракт допускает работу без оценки. При известной нехватке места показать проблему и действие смены назначения. После изменения выбора инвалидировать прежнюю оценку; запоздалый ответ не должен подменить свежую.

На запуске «Запускаем…». До ответа не объявлять скачивание начавшимся. Сохранить действующую идемпотентность: повтор после потери ответа использует правильный ключ, а новая пользовательская задача получает новый. Ошибка запуска не сбрасывает выбор.

### 5.8. Скачивание

Компактная карточка: название состояния, процент и переданный объём, доступное действие, тонкая полоса 6 px, ниже скорость/время и путь. Высота определяется содержимым. Не оставлять большую пустую зону под прогрессом.

Все значения из backend. При неизвестном общем объёме — неопределённый прогресс и переданный объём, без выдуманного процента. Время — оценка, не обещание. После 100 % передачи могут оставаться серверные операции; завершение показывать по терминальному статусу задачи.

Пауза/продолжение — только если API их действительно поддерживает. Если имеется лишь остановка, назвать действие «Остановить» и показать честное последующее поведение. Не переименовывать остановку в паузу ради совпадения с макетом.

Различать ожидание, запуск, скачивание, паузу при её поддержке, завершение, ошибку, отмену и потерю связи. При потере связи не объявлять задачу упавшей. Не утверждать, что оборванный файл продолжится с байта остановки без подтверждения.

Сохранить доступ к существующим заданиям и истории, если они есть. Упрощённая карточка демо не является требованием скрыть остальные реальные задачи.

### 5.9. Уведомления

Общая область справа в пределах приложения, без перекрытия заголовка и основных действий. На mobile — вписывается в ширину. Успех исчезает примерно через 3–4 секунды. Важная ошибка остаётся возле проблемного элемента, пока её можно исправить; toast не должен быть единственным носителем ошибки.

Сообщения «Диск подключён», «Папка «…» создана», «Скачивание началось» появляются только после соответствующего успешного ответа. Повторный рендер не размножает уведомления и таймеры.

## 7. Реализация состояния и компонентов

Выделить или привести к общим примитивам: оболочку приложения, заголовок/футер диалога, кнопку, поле, переключатель метода, строку файла, строку назначения, карточку аккаунта, карточку задачи и уведомление. Переиспользовать существующий UI-kit. Не вводить новый framework ради редизайна.

Хранить отдельно: серверное состояние аккаунта/задач, черновик скачивания, навигацию, временный просмотр назначения, предпочтение темы. Переходы назад и смена темы не должны пересоздавать черновик. Закрытие мастера сохраняет черновик в рамках текущей страницы; восстановление после reload не обещать без существующего механизма.

Асинхронные ответы привязывать к актуальному запросу, аккаунту и назначению. Уход со страницы должен прекращать ненужные подписки/опросы либо игнорировать устаревший результат. Проверить несколько быстрых смен папки и темы, двойное нажатие запуска и смену способа авторизации.

Не выводить токены, пароли и полный JSON авторизации в логи, toast или диагностические скриншоты. UI-упрощения не должны включать режим удаления/перезаписи, который раньше требовал явного решения.

## 8. Адаптивность и доступность

Проверить ширины 320, 375/390, 768, 1024 и 1440 px, обе темы, масштаб текста/страницы 200 %. Нет горизонтального скролла страницы, столкновений заголовков и действий, обрезанных путей и потерянных нижних кнопок при экранной клавиатуре.

Desktop-диалог ограничен окном; скролл организован понятно, без нескольких бессмысленных вложенных областей. Mobile может использовать существующий полноэкранный диалог. Доступ к футеру сохраняется.

Семантические кнопки и поля, постоянные labels, понятные accessible names у крестика и иконок. Keyboard focus видим; модальный диалог управляет фокусом и возвращает его к инициатору. Escape закрывает согласно контексту, но не останавливает активную задачу. При вложенной форме сначала закрывать её. Не сбрасывать фокус при каждом обновлении прогресса.

Обновления статуса озвучивать умеренно; не объявлять каждое изменение процента. Поддержать reduced motion. Короткие переходы около 120–180 ms допустимы, если не мешают действию.

## 9. Проверки и критерии готовности

### Визуальная проверка — блокирует сдачу

- [ ] Светлая тема читается во всех экранах и состояниях, включая selected, hover, error, autofill, dropdown и toast.
- [ ] Контраст проверен по computed colors; приложены результаты проблемных и исправленных пар.
- [ ] Тёмная тема не ухудшена после исправления светлой.
- [ ] Несколько соседних выделенных строк не перекрываются, радиусы и отступы совпадают.
- [ ] Главный экран не имеет огромных пустых карточек; прогресс компактен.
- [ ] Используется одна типографическая система; однотипные поля выровнены.
- [ ] Проверены реальные браузерные скриншоты desktop/mobile в обеих темах. Unit-тесты не заменяют этот пункт.

### Функциональная регрессия

- [ ] Успешный вход ведёт на главный без назначения папки и экрана «Готово».
- [ ] Ошибки авторизации, истёкший код и недоступный способ входа обрабатываются честно.
- [ ] Смена метода не оставляет фоновый запрос предыдущего сценария активным бесконечно.
- [ ] Отмена выбора назначения сохраняет старый путь; подтверждение сохраняет новый.
- [ ] Создание папки обрабатывает успех, конфликт имени и отказ сервера.
- [ ] Смена назначения обновляет сведения «есть на сервере» и оценку объёма.
- [ ] Пустой, большой, частично загруженный список и ошибка списка различимы; обрезание результатов не скрыто.
- [ ] Ручной выбор, целый диск, вложенные файлы, ограничения и возврат назад сохраняют корректный состав задачи.
- [ ] Двойное нажатие и потеря ответа не создают дублирующую задачу в поддерживаемом сценарии.
- [ ] Прогресс, неизвестный объём, завершение, ошибка и потеря связи отображаются по реальным статусам.
- [ ] Выход во время работы соответствует реальному API и не показывает ложный успех.
- [ ] Смена темы не влияет на форму и состояние задачи; предпочтение переживает reload.

Проверять поведение и контракты. Использовать существующие тесты и дополнить их на изменённые переходы и регрессии. Не писать тесты, которые лишь повторяют CSS-константы или структуру реализации. Прогнать проектные lint/build/test команды; недоступные проверки явно перечислить.

## 10. Порядок выполнения и сдача

1. Проверить актуальный код и контракты, определить существующие точки расширения.
2. Исправить тему и общие стили, проверить контраст на ключевых поверхностях.
3. Переработать оболочку, первый экран, главный и аккаунт.
4. Упростить подключение и собрать сценарий скачивания с сохранением черновика.
5. Подключить реальные данные, ошибки, загрузочные состояния и уведомления.
6. Проверить геометрию, длинные тексты, обе темы и мобильную компоновку.
7. Выполнить необходимые тесты, браузерную проверку и устранить найденные регрессии.

В сдаче предоставить: краткое описание изменений; список изменённых модулей; результаты проверок; реальные скриншоты главного экрана, выбора, авторизации и прогресса в обеих темах; остаточные ограничения. Скриншоты с тестовыми данными. Указать, какие пункты зависят от backend и почему.

Не заявлять задачу завершённой, если светлая тема не проверена визуально, фиктивные действия заменяют API или один из основных сценариев недоступен. Не выполнять публикацию, push или merge без соответствующей авторизации. Текущее задание — реализовать проверяемый редизайн в проекте и подготовить результат к ревью.
