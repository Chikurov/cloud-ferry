# Функциональный аудит Cloud Ferry

Дата: 14 ноября 2026. Область: только `internal/httpapi/web/{index.html,app.js,style.css}`.
Go/API, деплой и CI не изменялись.

## Метод и охват

- Реальный Go-сервер `bin/cloudferry` (`cmd/cloudferry`) с `state.json`, в котором
  есть аккаунт и активное задание; движок rclone заменён детерминированным fake rc
  на unix-сокете (`core/version`, `operations/about|list|stat|size`, `sync/copy`,
  `job/status`, `job/stop`, `config/*`).
- UI гонялся в headless Chrome 157 через CDP: клики, клавиатура, фокус, диалоги,
  тосты, сетевые ошибки, console. Для недостижимых без внешних сервисов состояний
  (needs-auth, офлайн, 4xx/5xx, device flow, лимит папок) использован
  детерминированный overlay `fetch`; остальные запросы шли в реальный сервер.
- Viewport: 1000×780, 500×780, 390×844. Проверялись `scrollWidth == innerWidth`,
  попадание меню/диалога в viewport, клавиатурный порядок и фокус-трап.
- Итог: **244 автоматические проверки, 244 пройдено, 0 провалено**.
  Машинный отчёт: audit-report.json.

Статусы в таблице: **ок** — работало и проверено; **исправлено** — поведение
изменено в web-файлах; **требует backend** — без изменения API/модели данных
не решается (в рамках задачи не исправлялось).

## Что исправлено (web-файлы)

1. Мастер: «Отмена» на первом шаге и возврат на главный экран; Enter отправляет шаг; guard от повторного/параллельного подключения.
2. Онбординг: инструкция для WebDAV (Яндекс 360, ссылка, 2–3 часа), инструкция для OAuth (ссылка, права, redirect), требование полного JSON для токена и клиентская проверка.
3. Device flow: срок действия кода, блокировка полей, guard повторного старта, озвучивание кода/отмены, фокус на «Подключиться» после ошибки/истечения.
4. Пикеры: открытие серверного пикера в введённом пути, корректный текст облачной 404, очистка ошибки сводки при открытии.
5. Диалоги: явная очистка/возврат фокуса и фокус-трап вместо ненадёжного `close`-события после Esc в Chrome 157; устойчивый возврат фокуса при гонке с нативной реставрацией.
6. Главный экран: guard двойного «Скачать», guard повторных stop/resume, сохранение фокуса после паузы/продолжения, пауза для queued, скрытие мёртвой паузы при verifying, источник в состоянии «Готово».
7. Ошибки и повторы: «Повторить» у проверки подключения, копирования списка, обновления неизвестного статуса; понятные состояния и guard для needs-auth.
8. Неизвестный статус задания: отдельный экран «Неизвестное состояние» с «Обновить».
9. Меню/выход: возврат фокуса и закрытие меню при уходе из диалога.
10. CSS: оформление inline-кода в инструкциях мастера.

## Что осталось / требует backend

- **Список заданий и история.** На экране видно только самое новое активное задание;
  остальные активные задания и историю нельзя открыть. Нужен отдельный экран и,
  возможно, уточнение API.
- **Остановка проверки целостности.** `jobs.Manager.Stop` принимает только
  `running`/`queued`; если пользователю нужно прерывать `verifying`, это изменение
  Go/API, не UI. Сейчас кнопка скрыта, чтобы не было гарантированной ошибки.
- **Мультиаккаунт.** API позволяет хранить несколько аккаунтов, но UI работает с
  последним; удаление старого аккаунта при активном задании конфликтует. До
  появления переключателя аккаунтов в шапке оставлено только предупреждение.
- **Реальный Яндекс.** Device flow, OAuth-обмен и WebDAV-подключение проверялись
  на контрактах реального Go-сервера с детерминированными ответами external API;
  реальные запросы к Яндексу в этой среде не выполнялись.
- **Chrome 157 quirk.** После закрытия `<dialog>` по Esc браузер не присылает
  `close` при следующем закрытии; это обойдено явными вызовами очистки/фокуса,
  но при обновлении браузера стоит перепроверить.
