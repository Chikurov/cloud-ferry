# Cloud Ferry: устройство и безопасность

Документ описывает, как приложение устроено внутри: контейнеры, сокет движка,
тома, формат состояния, восстановление задач и защитные механизмы. Пользователю
это не нужно — ему адресовано [руководство](USER-GUIDE.md).

## 1. Общая схема

```
браузер (Umbrel, порт 8741)
   │  HTTP, cookies Umbrel
   ▼
app_proxy ──► api (Go, :3000) ──unix-сокет──► rclone (rcd)
                 │                             │
                 ├─ /data/state.json           ├─ /config/rclone.conf
                 └─ /downloads, /destination   └─ /downloads, /destination
```

Два контейнера и прокси Umbrel:

| Сервис | Что делает | Что снаружи |
|---|---|---|
| `app_proxy` | Проксирует порт `8741` на `api:3000`, авторизация — логин Umbrel | единственная точка входа |
| `api` | Go-бинарник `cloudferry`: отдаёт интерфейс и JSON API, хранит состояние, управляет задачами, создаёт remote'ы | только через `app_proxy` |
| `rclone` | `rclone rcd` 1.76.0: движок скачивания, доступен только по unix-сокету | портов нет |

`api` собран на образе rclone, поэтому в контейнере есть и бинарник приложения,
и движок для `--spawn-rclone` в standalone-режиме. В Umbrel движок — отдельный
контейнер.

`hooks/pre-start` выполняется перед каждым стартом приложения и удаляет
осиротевшие `*.sock` в `data/run`: rclone не снимает свой сокет при аварийной
остановке, и без очистки следующий запуск падает с `address already in use`.
В `deploy/standalone` ту же роль играет одноразовый сервис `prepare`.

Оба контейнера работают от `1000:1000`, имеют healthcheck:

- `api` — сам бинарник с флагом `-healthcheck` (не нужны curl/wget и работает
  при basic-auth);
- `rclone` — аутентифицированный `core/version` по сокету, а не просто
  `test -S`, иначе устаревший файл сокета выглядел бы как живой движок.

## 2. Поток данных

1. Браузер запрашивает `GET /api/state` (аккаунты, задачи, папка по умолчанию и
   разрешённые корни) и `GET /api/system` (свободное место корней, квота
   облака, версия). Опрос идёт раз в 2,5 с, с backoff до 30 с; на скрытой
   вкладке опрос останавливается и возобновляется при возврате.
2. Подключение облака. Интерфейс сначала вызывает
   `POST /api/accounts/validate`: сервер проверяет доступ, создав временный
   remote `cfcheck_…` (он удаляется сразу после проверки), и только после
   успеха — `POST /api/accounts`, который создаёт remote
   через `config/create` и запись аккаунта в `state.json`. Пароль сохраняется в
   `rclone.conf` в obscured-виде, токен — как есть; в `state.json` остаются имя
   remote и логин, но не пароль и не токен.
3. Вход через Яндекс по коду. `GET /api/oauth/yandex/status` сообщает,
   настроено ли своё OAuth-приложение (`available: true`); тогда мастер
   показывает способ «Войти через Яндекс» первым и работает через
   `POST /api/oauth/yandex/device/start`,
   `GET /api/oauth/yandex/device/{id}` и `DELETE /api/oauth/yandex/device/{id}`.
   Пользователь вводит код на `oauth.yandex.ru/device`, redirect URI не нужен.
4. Выбор источника: `GET /api/accounts/{id}/folders` и `/files` читают облако
   через `operations/list`; `POST /api/cloud/sizes` — через `operations/size`.
5. Папка на сервере: `GET /api/fs/folders` (алиас `/api/fs/dirs`),
   `POST /api/fs/dirs` для создания одной папки; `POST /api/jobs/existing`
   проверяет, какие выбранные папки уже есть в папке назначения (только верхний
   уровень, без рекурсии, размеров и записи).
6. Проверка: `POST /api/preflight` считает объём (`operations/size`), свободное
   место (`statfs`), возвращает `files`, `bytes`, `free`, `fits`. `fits`
   сравнивается с тем же порогом 90 % свободного места, что и `--max-transfer`
   при запуске.
7. Запуск: `POST /api/jobs` создаёт запись и вызывает `sync/copy` с include-
   правилами по выбранным папкам и файлам. Интерфейс всегда отправляет
   `mode=copy` и ключ идемпотентности `clientToken` (подробнее в разделе 6);
   повтор с тем же ключом возвращает уже созданную задачу с ответом 200 и
   заголовком `Idempotent-Replay: true`, а не создаёт вторую. Ответ при первом
   создании — 201.
8. Прогресс: менеджер задач опрашивает `job/status` и `core/stats` раз в 2 с,
   пишет статистику в `state.json`; интерфейс получает её через `/api/state`.
   Если движок дольше двух минут подряд отвечает ошибкой на `job/status`,
   задача помечается прерванной, а не висит вечно.
9. Пауза — `POST /api/jobs/{id}/stop` (`job/stop`); запись получает статус
   `canceled`, а интерфейс показывает «Пауза», потому что движок не умеет
   возобновлять задачу. Продолжение — `POST /api/jobs/{id}/resume`: сервер
   проверяет, что источник ещё существует, а старая задача движка
   действительно мертва, и создаёт новую `sync/copy`.

В интерфейсе окно скачивания открывается сразу на шаге «Что скачать»:
проверка идёт следом, а шаг «Куда сохранить» открывается кнопкой
«Изменить» у строки «Папка на сервере» на проверке.

Своё OAuth-приложение Яндекса включается переменными `CF_YANDEX_CLIENT_ID` и
`CF_YANDEX_CLIENT_SECRET` (алиасы `YANDEX_CLIENT_ID`/`YANDEX_CLIENT_SECRET`);
нужны обе. Секрет остаётся в окружении `api` и в конфиге rclone (без него не
обновить токен), но не попадает в `state.json` и логи: в лог пишется только
публичный `client_id`. Старые ручки `POST /api/oauth/yandex/start` и
`.../finish` остались для совместимости, новый интерфейс их не использует.

Все обращения к движку идут через `internal/rc`: клиент умеет только методы из
allowlist. Это принципиально: rc-API rclone эквивалентен shell-доступу от имени
пользователя rclone (запуск команд, чтение конфигурации, произвольные файлы).

Разрешённые методы (`internal/rc/methods.go`):

```
sync/copy      sync/sync      job/status     job/stop
core/stats     core/version
operations/list  operations/stat  operations/size  operations/about
operations/check
config/create  config/delete  config/get
```

Запрещены, в частности, `core/command`, `core/quit`, `config/dump`,
`config/setpath`, `operations/getfile`, `operations/uploadfile`,
`operations/purge`, `mount/*`, `serve/*`, `vfs/*`, `debug/*`,
`backend/command`. Запрос вне allowlist отклоняется до обращения к сокету.

## 3. Тома и файлы

В Umbrel (`cloudferry-migrator/docker-compose.yml` и манифест приложения):

| Том в контейнере | Где смонтирован | Откуда | Что лежит |
|---|---|---|---|
| `/data` | `api` | `${APP_DATA_DIR}/data/state` | `state.json`, `state.json.bak` |
| `/run/rclone` | `api`, `rclone` | `${APP_DATA_DIR}/data/run` | `rclone.sock` |
| `/config` | `rclone` | `${APP_DATA_DIR}/data/rclone` | `rclone.conf` с доступами |
| `/cache` | `rclone` | `${APP_DATA_DIR}/data/cache` | кэш rclone (VFS/метаданные) |
| `/downloads` | `api`, `rclone` | папка Downloads Umbrel (`folderAccess`) | файлы по умолчанию |
| `/destination` | `api`, `rclone` | второй слот `folderAccess` (необязательно) | вторая папка на сервере |

`api` не монтирует `/config` и `/cache`: конфиг и кэш — дело движка, приложение
их не читает. Корни назначения приходят из `DEST_ROOTS` (`/downloads` по
умолчанию; в Umbrel `DEST_ROOTS=/downloads,/destination`). Если
необязательный слот не заполнен, `folderAccess` не создаёт mount, и при старте
такой корень пропускается: писать в него означало бы писать в слой контейнера и
потерять файлы после перезапуска.

`rclone.conf` не попадает в резервные копии Umbrel (`backupIgnore`), как и
`data/cache` и `data/run` — токены не уходят в бэкап. После восстановления
устройства облако нужно подключить заново.

## 4. `state.json`

Один JSON-файл, единственный писатель под мьютексом:

```json
{
  "accounts": [
    {
      "id": "…",
      "name": "Яндекс Диск",
      "provider": "webdav | yandex-token | yandex-oauth",
      "login": "…",
      "remote": "cf_…",
      "createdAt": "…",
      "status": "ok | needs-auth | unknown",
      "statusNote": "…",
      "checkedAt": "…"
    }
  ],
  "jobs": [
    {
      "id": "20261118T120000-ab12cd34",
      "accountId": "…",
      "idempotencyKey": "…",
      "source": "cf-…:",
      "sourcePaths": ["Фотографии"],
      "sourceFiles": ["Документы/договор.pdf"],
      "dest": "/downloads",
      "mode": "copy",
      "status": "queued | running | verifying | done | failed | interrupted | canceled",
      "group": "migrate/…",
      "rcloneJobId": 12,
      "executeId": "…",
      "error": "…",
      "errorTitle": "…",
      "errorAdvice": "…",
      "stats": { "bytes": 0, "totalBytes": 0, "speed": 0, "eta": 0, "transfers": 0, "totalTransfers": 0, "errors": 0, "elapsedTime": 0 },
      "check": { "hashType": "…", "matched": 0, "differ": 0, "missingOnDst": 0, "broken": 0, "checkedAt": "…" },
      "failures": ["…"],
      "failureCount": 0,
      "createdAt": "…",
      "startedAt": "…",
      "finishedAt": "…"
    }
  ]
}
```

Поля записаны с `omitempty`: у старой задачи может не быть `idempotencyKey`,
`sourcePaths`, `check` и других добавленных позже полей.

Свойства:

- учётных данных в файле нет — только имя remote и логин; пароли и токены
  лежат в `rclone.conf`;
- запись атомарная: временный файл, `fsync`, `rename`, `fsync` каталога; режим
  `0600`;
- перед заменой текущая версия копируется в `state.json.bak`, но только если
  она читается как JSON. После восстановления повреждённый файл не затирает
  последнюю хорошую копию;
- при повреждении основного файла `Open` читает `.bak`, восстанавливает
  состояние и сразу перезаписывает основной файл;
- история ограничена 100 задачами. Активные (`queued`, `running`, `verifying`)
  и задачи с ещё действующим ключом идемпотентности не вытесняются, поэтому
  файл может временно превысить 100 записей;
- список неудачных файлов в задаче хранится до 200 путей; `failureCount` может
  быть больше;
- `state.json` лежит в `data/state`, а не в общем `/downloads`.

## 5. Восстановление после перезапуска

`Manager.Recover()` вызывается до старта поллинга:

| Что было в файле | Что делает приложение |
|---|---|
| `queued` | помечает `interrupted` с текстом «Приложение перезапустилось до начала скачивания» |
| `running`, движок ответил `finished` | записывает настоящий итог — `done` или `failed` |
| `running`, движок знает задачу и она ещё идёт | оставляет `running`, поллинг продолжает прогресс |
| `running`, задачи в движке нет или она чужая (`executeId`) | помечает `interrupted` с текстом «Приложение перезапустилось во время скачивания» |
| `running`, движок недоступен | оставляет запись; поллинг разберётся, когда сокет поднимется |

`interrupted` и `canceled` в интерфейсе показываются как «Пауза» с кнопкой
«Продолжить». `Resume` проверяет, что источник ещё существует, что старая задача
движка действительно мертва, и только затем создаёт новую `sync/copy` с
сохранённым режимом. Уже скачанные файлы rclone пропускает; недокачанный файл
начинается заново — это поведение движка, а не приложения.

## 6. Идемпотентность запуска и лимиты

**Ключ идемпотентности.** `POST /api/jobs` принимает необязательный ключ: сначала
заголовок `Idempotency-Key`, иначе поле `clientToken`. Формат —
8–128 символов `[A-Za-z0-9._:-]`. Интерфейс считает ключ из канонического
выбора (аккаунт, источник, назначение, режим), поэтому повтор после потери
ответа отправляет тот же ключ и получает уже созданную задачу. Повтор в
пределах 24 часов (и пока задача не вытеснена из истории) возвращает 200 с
`Idempotent-Replay: true` и тем же `id`; ключ с другим выбором,
аккаунтом или назначением — 409 `idempotency_conflict` с полем `clientToken`.
Если ответ потерян, интерфейс повторяет запрос до двух раз с тем же ключом,
прежде чем сообщить, что запуск не подтверждён.

**Лимиты.**

- `mode=copy`: файлы добавляются и обновляются, но не удаляются. Режим `sync`
  API принимает, но интерфейс его не предлагает, а в корень `/downloads` он
  запрещён: иначе удалил бы лишнее в общей папке.
- Перед запуском вычисляется `--max-transfer`: 90 % свободного места
  (`disk.TransferLimit`), чтобы не заполнить диск полностью; при нехватке
  места задача останавливается штатно и получает понятную причину. Проверка
  объёма использует тот же порог.
- Один запуск: до 20 папок и 100 отдельных файлов, проверка и на клиенте, и на
  сервере после нормализации (дубликаты и потомки выбранных папок не
  считаются).
- Пустой список источника означает весь диск; лимиты 20/100 к нему не
  применяются.
- Путь в облаке — до 1024 символов, без `..` и управляющих символов.
- `operations/size` для проверки ограничен 10 минутами; отменить серверный
  обход нельзя — прерывается только HTTP-запрос клиента. При уходе со шага
  обход может продолжаться до 10 минут.
- `POST /api/cloud/sizes` считает до 20 папок за запрос (параллельно 4), ответ
  кэшируется на 10 минут; пункт с ошибкой приходит отдельным элементом, а не
  роняет весь ответ.
- `/files` отдаёт не больше 200 файлов (по умолчанию 50); ответ кэшируется на
  2 минуты. Список папок — не больше 500 подпапок в одном уровне, с признаком
  `truncated`; кэш списков папок — 60 секунд. Курсора для следующей страницы
  нет.
- Одновременных передач по умолчанию 8 (`CLOUDFERRY_TRANSFERS`), checker'ов 16,
  `tpslimit` 20 — ниже лимита Яндекса.
- Список задач ограничен 100 записями; история старше вытесняется.
- Убрать завершённую задачу с главного экрана можно только в браузере
  (`localStorage`); на сервере задача остаётся.

## 7. Безопасность

**Пути.** Все пути назначения проверяются по `DEST_ROOTS`:

- `fsbrowse.ValidateDest` нормализует путь и требует, чтобы он лежал внутри
  одного из корней; `..`, выход за корень и симлинк отклоняются;
- просмотр, проверка существования и создание папок идут через `os.Root`
  (`os.OpenRoot`), поэтому ни `..`, ни симлинк не могут вывести за пределы
  корня;
- `Mkdir` создаёт ровно одну папку внутри корня: родитель должен существовать,
  имя не может быть пустым, `.` или `..`, путь ограничен 4096 символами;
- проверка, какие папки уже есть на сервере (`POST /api/jobs/existing`),
  смотрит только верхний уровень выбранной папки, не ходит рекурсивно и не
  считает размеры; симлинк не считается существующей папкой;
- источники в облаке очищаются отдельно: без ведущего `/`, без `..`, длина до
  1024 символов.

**Адрес WebDAV.** Подключение по паролю приложения допускает только хосты
из списка `defaultWebDAVHosts` (`webdav.yandex.ru`). Список расширяется
переменной `CF_WEBDAV_HOSTS` (через запятую) без пересборки, а всё остальное
отклоняется до обращения к сети: так исключены обращения к локальной сети и
DNS-имена, ведущие внутрь. Адреса loopback, приватных сетей, link-local и
числовые формы IPv4 отклоняются отдельной проверкой.

**Секреты.** Пароль приложения и токен передаются один раз в `api`, уходят в
`rclone.conf` и не сохраняются в `state.json`, ответах API и логах. Секрет
собственного OAuth-приложения (`CF_YANDEX_CLIENT_SECRET`) читается только из
окружения, не из аргументов командной строки (argv виден локальным процессам),
и в лог попадает только публичный `client_id`. `rclone.conf` исключён из
резервных копий Umbrel.

**API.**

- В Umbrel собственного секрета у API нет: доступ закрывает `app_proxy` и логин
  Umbrel. `CF_BASIC_USER`/`CF_BASIC_PASS` — необязательный слой для
  standalone-запуска, по умолчанию выключен.
- Тело запроса ограничено 1 МиБ, JSON разбирается строго
  (`DisallowUnknownFields`, запрет хвостовых данных).
- Наружу отдаются короткие пользовательские фразы; техническая причина уходит
  в лог, а не в браузер.
- Эндпоинт виджета `/api/widget` отвечает без cookies: в Umbrel у API нет своей
  авторизации, поэтому запрос с домашнего экрана проходит. Он отдаёт только
  агрегат прогресса.
- Файлы интерфейса встроены в бинарник (`go:embed all:web`): отдельного
  веб-сервера нет, отдаёт их `api`.

**Движок.** rclone не публикует порт, слушает только unix-сокет с basic-auth
(`RC_USER`/`RC_PASS` из `APP_CLOUDFERRY_RC_*`). Приложение не проксирует rc-API
целиком, а вызывает только разрешённые методы.

## 8. Ограничения

- Интерфейс рассчитан на один аккаунт Яндекс Диска: показывает последний
  созданный, а при новом подключении удаляет старое.
- Пароль приложения требует Яндекс 360; вход по коду и токену — нет.
- Альбомы «Фото» и история версий не скачиваются.
- Недокачанный файл после паузы или перезапуска скачивается заново.
- Шаг «Куда сохранить» не переключает корни: он открывается в текущем пути и
  ходит вверх только до своего корня. Переключателя корней в интерфейсе нет,
  поэтому второй слот `folderAccess` (`/destination`) сейчас объявлен в
  манифесте, но выбрать его из интерфейса нельзя.
- Оценку объёма нельзя отменить на сервере; при уходе со шага обход может
  продолжаться до 10 минут.
- Пагинации в API нет: большие папки и списки файлов показываются частично.
- Статус `verifying` зарезервирован, но текущий API его не выставляет: проверка
  целостности запускается только вручную через `POST /api/jobs/{id}/check`, и
  её результат не показывается в интерфейсе.
- История задач ограничена 100 записями и не является журналом аудита.
- Виджет показывает только активное скачивание (одно, с прогрессом); без него —
  «Нет активных скачиваний».

## 9. Эксплуатация

- `GET /api/healthz` — процесс жив и всегда отвечает 200; если движок
  недоступен, в теле `ok: false` и короткая причина. `GET /api/readyz` — API и
  движок готовы (503, если rclone недоступен).
- Health-checker стартует через 5 секунд после запуска, затем раз в 30 минут
  проверяет каждый аккаунт через `operations/about` и переводит его в
  `needs-auth` при 401/403/410; интерфейс предупреждает до того, как скачивание
  упадёт.
- `GET /api/system` отдаёт свободное место, квоту облака и версию; квота
  кэшируется на 60 секунд и обновляется в фоне, поэтому интерфейс не ждёт
  облако.
- После аварийной остановки достаточно перезапустить приложение: `pre-start`
  уберёт устаревший сокет, `Recover` разберёт задачи, `readyz` подтвердит
  готовность.
