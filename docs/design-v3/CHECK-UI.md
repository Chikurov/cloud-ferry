## 1. Что добавлено

### 1.1. Действие «Проверить файлы»

В карточке задачи, которая уже не пишет файлы (`done`, `failed`,
`interrupted`), появилась строка-действие `button.btn--secondary.btn--sm` с
иконкой-галочкой и подписью «Проверить файлы». Условия совпадают с сервером:
эти три статуса принимает `Manager.Check`; для `running`, `queued`,
`verifying` и `canceled` строки нет (задача ещё двигает файлы или сервер
отклонит проверку).

Состояния строки (одна карточка — одна строка, дублей нет):

| Состояние | Что видно | Поведение |
|---|---|---|
| `job.check` есть в `/api/state` | результат сразу, без кнопки | кнопка не рисуется вовсе |
| запрос в полёте | «Проверяем…» со спиннером, `aria-busy="true"`, `aria-disabled="true"` | повторный клик и Enter игнорируются, фокус остаётся на кнопке |
| 200 | «Все файлы на месте» либо «Проверено: N файлов» + расхождения | кнопка исчезает, фокус переходит на результат |
| 409 | сохранённый результат из `job.check` | тихое обновление `/api/state`, без тоста об ошибке |
| 502 | «Не удалось проверить файлы» + «Повторить» | inline у карточки, статус/прогресс задачи не меняются |
| потеря связи | общая полоса «Нет связи с сервером» | ошибка проверки не рисуется; после восстановления опрос подтягивает `job.check` |

### 1.2. Тексты результата

- Всё совпало: спокойная строка **«Все файлы на месте»** (зелёная
  галочка) + приглушённая вторая строка «Проверено: 12 файлов ·
  сегодня, 20:40».
- Есть расхождения: **«Проверено: N файлов · <дата>»** (янтарная
  иконка-предупреждение) и под ней **«Нет на сервере: N · Отличаются: N ·
  Ошибки: N»**. Порядок и формулировки — как в задаче.
- `N` в «Проверено» — сумма `matched` и всех расхождений: сервер присылает,
  сколько файлов совпало и сколько нет, интерфейс не досчитывает их сам.
- Числа форматируются `Intl.NumberFormat('ru-RU')` и склоняются через
  существующий `formatFiles()` («1 файл», «2 файла», «12 файлов»); счётчики
  в строке расхождений — с разрядами, без склонения.
- Время — существующий `checkedAtText()`: «сегодня, 20:40» или дата.

### 1.3. Сеть, ошибки и гонки

- `checkJob(id, trigger)` — отдельный обработчик действия. Состояние
  `busy`/`error` хранится по `job.id` (как `jobActionBusy` у паузы), поэтому
  перерисовка от опроса не сбрасывает «Проверяем…» и не теряет inline-ошибку.
- Клиентский таймаут проверки — 10 минут (`API_TIMEOUT.check`), сервер
  отводит проверке до 2 часов: клиент не должен обрывать долгую проверку
  раньше времени и выдавать её за потерю связи.
- 409 обрабатывается без тоста: `loadData()` + `render()`, дальше решает
  наличие `job.check`. Если параллельная проверка ещё идёт и результата
  пока нет, строка возвращается к действию — повторный клик безопасен
  (сервер снова ответит 409).
- `status === 0` (fetch упал, сеть/таймаут) — это связь, а не проверка:
  `setOffline(true)`, `announce('Нет связи. Проверка не запущена.')`,
  никакой inline-ошибки. Результат появится следующим опросом, если сервер
  успел сохранить `job.check`.
- Любой другой не-200 ответ сервера — inline «Не удалось проверить файлы» с
  «Повторить»; карточка задачи и её прогресс не меняются.
- Сохранённый результат не «перечитывается» на каждом опросе: строка
  обновляется только при смене ключа (статус, busy/error, счётчики,
  `checkedAt`) — `aria-live`-регион не перечитывает одно и то же каждые
  2,5 секунды.

### 1.4. Доступность

- Действие — настоящий `button` с `type="button"` и доступным именем
  «Проверить файлы»; активация с клавиатуры (Tab + Enter) проверена в
  браузере.
- Результат — `div[role="status"][aria-live="polite"][aria-atomic="true"]`
  с `tabindex="-1"`: после действия фокус переходит на него, поэтому
  сообщение и озвучивается через фокус, и попадает в live-регион.
- «Проверяем…» остаётся видимым текстом, а не только спиннером; у кнопки
  есть `aria-label="Проверяем файлы"`, `aria-busy` и `aria-disabled`
  (кнопка не выпадает из порядка фокуса, в отличие от `disabled`).
- Смысл не передаётся только цветом: у успеха галочка, у расхождений и
  ошибки — иконка-предупреждение и разные тексты.
- `prefers-reduced-motion` уже гасит анимации глобально (блок в
  `style.css`), спиннер под него попадает.

### 1.5. Стиль и 390 px

- Используются только существующие токены: `--surface`, `--ink`,
  `--muted`, `--ok`, `--amber`, `--focus`, `--text-sm`, `--text-xs`,
  `--r-xs`; отдельного «своего» цвета нет, обе темы получают значения из
  `:root[data-theme]`.
- Строка живёт в обычном потоке `.now-body` карточки: без absolute,
  без фиксированной высоты и без выхода за границы карточки. На 390 px
  длинная строка расхождений переносится, горизонтального скролла нет.
- Действие — вторичная компактная кнопка `.btn--sm` (на coarse-pointer
  остаётся 44 px через общий медиазапрос), ошибка — строка с кнопкой
  «Повторить» без отдельной панели.

## 4. Совместимость с backend и найденный разрыв

Контракт сверен с кодом: `internal/store/store.go` (`CheckResult`:
`hashType`, `matched`, `differ`, `missingOnDst`, `broken`, `checkedAt`),
`internal/jobs/manager.go` (`Check`: только `done`/`failed`/`interrupted`,
повторно — `ErrConflict`, результат пишется в `job.check`),
`internal/httpapi/server.go` (`handleCheckJob`: 200 / 409 / 502 / 404).
Mock API повторяет именно эту форму ответа.

**Разрыв (backend, не исправлялся — задача запрещает менять Go):**
`CheckResult.matched` нигде не заполняется. `Manager.Check` разбирает из
ответа rclone `hashType`, `missingOnDst`, `differ`, `error`, а список
совпавших файлов (`match` в ответе `operations/check`) не читает; поле
`Matched` в `internal/store/store.go` объявлено, но присваивания нет.
Поэтому реальный `/api/state` сейчас отдаёт `matched: 0` при любом итоге.

Интерфейс это переживает без ложных чисел: при `matched: 0` и отсутствии
расхождений показывается «Все файлы на месте» без «Проверено: 0 файлов»
(сценарий `zero` в проверках); при расхождениях «Проверено: N файлов»
считает хотя бы известные файлы. Когда backend начнёт заполнять `matched`,
счётчик станет полным без правок UI. Исправление на стороне backend:
добавить в `out` поле `Match` с json-тегом `match` и
`Matched: len(out.Match)`.

Косвенно это же — единственный известный несверенный пункт контракта:
форму остальных полей `/api/state` UI получил и отрисовал корректно.

## 5. Ограничения проверки

- Проверка шла на mock API: реальный `operations/check` требует Яндекс.Диска
  и rclone, в этой среде не запускался. Форма ответа и коды взяты из кода
  backend и его тестов.
- Если проверка на сервере идёт дольше 10 минут, клиентский таймаут
  сработает раньше серверного (2 часа) и покажет общую потерю связи; при
  сохранённом результате следующий опрос всё равно покажет его. Для очень
  больших дисков таймаут клиента стоит увеличить или сделать отдельным
  состоянием «проверка продолжается на сервере».
- 409 при параллельной проверке без сохранённого результата возвращает
  строку к действию (без ложной ошибки); это редкий сценарий, отдельного
  сообщения «проверка уже идёт» нет.
- Коммит не делался.
